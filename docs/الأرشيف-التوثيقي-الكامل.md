# القسم 3 — التقييمات والقرارات المعمارية (نقد kimi وما اعتمدناه)

## 3.1 المبادئ الست غير القابلة للكسر (اعتُمدت بلا تجاوز)

| # | المبدأ |
|---|--------|
| 1 | لا نقل ملف قاعدة أبداً — دلتا فقط |
| 2 | كل جهاز نسخة كاملة (لا مصدر حقيقة وحيد) |
| 3 | هوية الصف = SyncId (UUID) — المطابقة بالمعرّف فقط |
| 4 | لا قرار «من يفوز» آلياً — كشف تعارض → جدول خلافات |
| 5 | الأرقام التراكمية مبنية من العمليات — لا تُزامَن القيمة |
| 6 | لا حذف فعلي — تعطيل أو tombstone |

## 3.2 القرارات الست لنقد kimi (اعتُمدت في الوثيقة v1.1)

1. **Seq عند Commit لا عند إنشاء الصف** — كل عملية تجارية = سطر واحد في `OperationLog` يأخذ Seq واحداً بعد نجاح الحفظ كاملاً، وكل صفوف العملية تشير إليه (شرط مجمّد).
2. **مسار كتابة موحّد (Unit of Work)** — يضمن ذرّ Seq + سجل العملية + تعيين `SyncId`/`OriginDevice`؛ الحفظ المباشر من الـ ViewModel ممنوع للعمليات التجارية (شرط مجمّد).
3. **ترتيب الإنشاء الحاسم**: `OperationLog` قبل `CloseDay`/`StockAdjustment` — لأن الإقفال والتسوية هما أنفسهما عمليات تُسجَّل في السجل.
4. **تمييز الجدولين**: `OperationLog` (أعمال/تدقيق، يمنح Seq) مقابل `SyncLog` (نقل الشبكة، المرحلة 2) — وحدة المزامنة = العملية لا الصف.
5. **المزامنة ليست نسخاً احتياطياً** ⚠️ — نسخ ليلي مستقل (SQLite Backup API) + تمرين استعادة دوري كل ربع («نسخة بلا اختبار استعادة = خيال»).
6. **السياق المنزلي**: UDP Broadcast + Heartbeat مع تحمّل تغيّر IP، إعادة محاولة بفواصل متدرجة + jitter، مفتاح سري + تقييد منفذ في Windows Firewall + HMAC بالتسلسل ضد replay، بوابة إصدارات Schema، مصافحة إقران بموافقة MAIN.

## 3.3 قرارات الشغْل والأدوار (v1.1)

- **الاعتماد = عملية `CloseDay` صريحة** أو أول مزامنة ناجحة (أيهما أسبق)؛ **فترة سماح** قبل الإقفال للتصحيح المسجَّل.
- التصحيح بعد الاعتماد = عملية جديدة: سند استرجاع / فاتورة Void / قيد عكسي — لا تعديل ولا حذف.
- **`StockAdjustment`** نوع رسمي للجرد: سبب **إجباري** + موقّع من مسؤول + غير قابلة للتعديل (تُصحَّح بتسوية مضادة).
- **البيع لا يُحجب بسبب خلاف بأي حال** — يُباع بالقيمة المحلية الظاهرة ويُوسَم «قيمته قيد المراجعة».
- **ملكية «الفاتورة المشتركة» = `OriginDevice`** (من ضغط حفظ)؛ أثر كل سطر يخصم من **مالك فئة المنتج** (الغطاء→A، الهاتف→P).
- **صيانة تستهلك قطع A**: `RepairPartUsage { product, qty, repairId }` من M — لا كتابة على صف منتج A (لا يدخل نطاق الخلافات).
- «الملكية تحدد من يعدّل لا من يحسب» — الأثر الحسابي نتيجة عمليات مسجّلة.

## 3.4 تقييم جودة التنفيذ (حتى 2026-09-10)
- بناء `0 Error(s) / 0 Warning(s)` بشكل متكرر.
- تحقق تشغيلي: قاعدة جُدّدت من الصفر → كل الـ 163 صنفاً حصلت `SyncId + OriginDevice` تلقائياً (خرائط التوحيد تعمل).
- ترقية قاعدة DEV قائمة دون حذف (مؤكّد فعلياً).
- إطلاق التطبيق واستمراريته (Smoke Test) دون انهيار.

```markdown
## 1. البنية العامة (Architecture)

### الأجهزة الأربعة وأدوارها

| الجهاز | الدور | المنتجات | الوظائف المسموحة |
|---|---|---|---|
| **الرئيسي (رقم 4)** | الخادم + المحاسبة | كل المنتجات (قراءة) | محاسبة، موظفون، تقارير، مزامنة مركزية |
| **رقم 1** | الإكسسوارات | منتجات الإكسسوارات فقط | بيع الإكسسوارات، مخزونها |
| **رقم 2** | الصيانة | قطع غيار الصيانة فقط | استقبال الأجهزة، صيانة، بيع قطع الغيار |
| **رقم 3** | الكاشير | **كل المنتجات + المخزون الكامل** | بيع الهواتف والإكسسوارات وقطع الغيار، نقطة البيع الكاملة |

**ملاحظات:** كل الموظفين يستطيعون رؤية تكاليف الشراء (ضروري وموافق عليه) — لا قيود على ذلك.

### كيف تحل مشكلة انقطاع الكهرباء

المشكلة: انقطاع الكهرباء = انقطاع الشبكة = توقف البيع. الحل مزدوج:

1. **تصميم Offline-First (يعمل دون شبكة):**
   - كل جهاز لديه قاعدة بيانات SQLite **محلية مستقلة** — البيع والمشتريات تُسجل محلياً فوراً.
   - وكيل مزامنة (Sync Service) ينقل التغييرات إلى الجهاز الرئيسي **تلقائياً** عند توفر الشبكة.
   - انقطاع الشبكة لا يوقف العمل إطلاقاً — أنت تبيع وتبيع، وتُزامن لاحقاً.
2. **UPS (أمر موصى به بشدة):**
   - UPS للجهاز الرئيسي + لسويتش الشبكة لضمان استمرار المزامنة أثناء الانقطاعات القصيرة.
   - UPS رخيص لأجهزة سطح المكتب (نصف ساعة إلى ساعة تشغيل).

### بنية البيانات

- **على كل جهاز (محلي):** جدول عمليات محلية (مبيعات، مشتريات، صيانة) + نسخة محدثة من كتالوج المنتجات الخاص بجهازه.
- **على الجهاز الرئيسي:** القاعدة المركزية الشاملة (كل المنتجات، الحسابات، الموظفون، السجلات من كل الأجهزة).
- **المزامنة:**
  - كتالوج المنتجات: من الرئيسي → الأجهزة.
  - المبيعات والمشتريات والصيانة: من الأجهزة → الرئيسي.
  - التعارضات نادرة (كل جهاز يخص نوعاً مختلفاً من المنتجات) وتُحل بـ "الأحدث يكتب".

### سلامة البيانات (حماية من انقطاع الكهرباء والإغلاق الخاطئ)

1. **معاملة ذرّية (Atomic Transaction):** كل بيع يُحفظ كاملاً أو لا يُحفظ — لا يوجد "بيع ناقص" أبداً.
2. **وضع WAL:** قاعدة SQLite محمية ضد انقطاع الكهرباء المفاجئ؛ عند إعادة التشغيل يستعيد النظام نفسه تلقائياً.
3. **قاعدة ثابتة:** زر "تأكيد البيع" يحفظ في القاعدة **قبل** الطباعة — لو انقطعت الكهرباء بعد التأكيد، البيع موجود.
4. **ترقيم تلقائي متسلسل للفواتير:** لا تكرار ولا فراغات في أرقام الفواتير.

## 2. الوحدات (Modules) والوظائف

### أ) إدارة المستخدمين والصلاحيات — الجهاز الرئيسي فقط
- مستخدمون بصلاحيات قابلة للتخصيص (مسؤول، محاسب، كاشير، فني صيانة، مدير مخزون).
- تسجيل دخول محمي بكلمة مرور.
- سجل نشاط (من فعل ماذا ومتى).

### ب) المنتجات والمخزون
- تصنيفات هرمية: هواتف، إكسسوارات، قطع غيار صيانة.
- خصائص المنتج: باركود، رقم تسلسلي (IMEI للهواتف)، سعر شراء، سعر بيع، كمية، حد أدنى للمخزون.
- **تنبيه نفاد المخزون:** تحذير تلقائي عند بلوغ الحد الأدنى + تقرير أصناف قاربت على النفاد.
- ربط كل منتج بجهازه (المخزن): إكسسوارات → جهاز 1، قطع صيانة → جهاز 2، هواتف → جهاز 3.

### ج) المشتريات
- فاتورة شراء من مورد، إضافة كميات للمخزن الصحيح.
- إرجاع مشتريات.
- حسابات الموردين (مدفوعات وأرصدة).

### د) نقطة البيع (POS) — أساساً على جهاز الكاشير
- فاتورة سريعة: إضافة بالباركود أو البحث، خصم، تعديل.
- **بحث فوري أثناء الكتابة:** بالاسم (عربي/إنجليزي)، الباركود، رقم IMEI للهواتف، أو التصنيف — يظهر النتائج دون ضغطة زر.
- طرق الدفع: نقدي / بطاقة / آجل (عملاء).
- **مرتجعات بنوعين:**
  - **مرتجع قصير المدى (خلال فترة قريبة):** إلغاء فاتورة كامل — البضاعة ترجع بسعرها الأصلي، المال يُعاد كاملاً، والحسابات تُعكس.
  - **مرتجع طويل المدى (بعد سنة أو أكثر — أمر شائع في الشركة):** معاملة خاصة — البضاعة **مستعملة**، يُتفق مع الزبون على مبلغ الإرجاع، تدخل المخزون كصنف **"مستعمل/مجدد"** بقيمة جديدة أقل، والفرق بين سعر البيع الأصلي ومبلغ الإرجاع يُسجل كتعديل محاسبي.
  - النظام يسأل عند كل مرتجع: حالة البضاعة، مبلغ الإرجاع، ويُقيد البند كمخزون مستعمل يُباع لاحقاً بسعره الجديد.
- طباعة فاتورة A4.

### هـ) الصيانة — جهاز الصيانة
- استقبال جهاز: بيانات العميل، نوع العطل، حالة الجهاز.
- سير الحالة: مستلم ← قيد الإصلاح ← منتهي ← مسلّم.
- **أجرة صيانة افتراضية** (قيمة قابلة للتعديل في الإعدادات).
- استخدام قطع الغيار يخصم من المخزون تلقائياً + يُضاف ثمنها للفاتورة.
- تحصيل أجرة الصيانة.

### هـ2) العمولات للبائعين (اختياري — بانتظار تأكيد)
- تسجيل البائع المسؤول عن كل فاتورة.
- تقرير عمولات شهري لكل بائع (نسبة مئوية من المبيعات أو مبلغ ثابت) يُضاف للراتب.

### و) المحاسبة — الجهاز الرئيسي
- **قيود اليومية (Debit/Credit)** بإدخال يدوي أو تلقائي من المبيعات والمشتريات.
- دليل الحسابات: أصول، خصوم، إيرادات، مصاريف، رأس مال.
- دفتر الأستاذ العام.
- **الميزان المراجعة** و**قائمة الدخل** و**المركز المالي**.
- إدارة الصندوق (النقدية) والمصروفات اليومية.
- استلام الإيرادات القادمة من كل جهاز آلياً عبر المزامنة.

### ز) الموظفون — الجهاز الرئيسي
- بيانات الموظفين، المرتبات، المسار الوظيفي.
- كشوف رواتب شهرية.

### ح) التقارير
- المبيعات: يومي/شهري/حسب الجهاز/حسب البائع.
- المخزون: كميات، نفاد، حركة أصناف.
- المحاسبة: ميزان مراجعة، أرباح وخسائر، دفتر أستاذ.
- تصدير: PDF و Excel.

4. **النسخ الاحتياطي:** نسخة يومية تلقائية على الجهاز الرئيسي.
5. **المرتجعات بعد فترة طويلة (سنة):** معاملة خاصة — تُسجل كصنف مستعمل بقيمة جديدة (كما في البند د).
6. **تكاليف الشراء:** مرئية لجميع الموظفين (مطلوب).
7. **أجرة الصيانة:** قيمة افتراضية قابلة للتعديل.
8. **العمولات للبائعين:** غير مطلوبة حالياً — تُضاف لاحقاً عند الحاجة.
```

```markdown
## 2. العمليات سجلّ دائم (شرط المبدأ 5)

- الفواتير (بيع/شراء/صيانة) والسندات **غير قابلة للتعديل أو الحذف بعد الاعتماد**.
- **الاعتماد = عملية `CloseDay` صريحة** (`إقفال اليوم/الوردية`) تقطع القفل، **أو أول مزامنة ناجحة، أيهما أسبق**.
- **فترة سماح:** ما قبل `CloseDay` (نفس الوردية) قابل للتصحيح مع تسجيل التعديل في `SyncLog` — الكاشير الذي يخطئ الباركود بعد ساعة لا يحتاج سنداً عكسياً.
- إذا عدّل جهازان نفس الفاتورة في فترة السماح قبل الإقفال → الخلاف يُسجَّل ويُرحَّل حسمه (البيع لا يُحجب).
- التصحيح بعد الاعتماد = عملية جديدة: سند استرجاع / فاتورة Void / قيد عكسي.
- **`StockAdjustment`** نوع عملية رسمي للجرد والتسوية (كسر/فقد/فرق عدّ/استلام غير مطابق):
  - سبب **إجباري** + موقّع من مسؤول (Admin).
  - هي نفسها **غير قابلة للتعديل**، وتُصحَّح بعملية عكسية (تسوية مضادة) إن اكتُشف خطأ إدخالها.
  - تُعتمد **دورة جرد دورية على MAIN** (شهرية مثلاً) لمقارنة الرقم المبني بعدد الرف.
- أثر مباشر على الكود الحالي: `PurchaseEditViewModel.Save()` يُقفل بعد `CloseDay`؛
  شاشة تعديل المشتريات تقتصر على فترة السماح.

### الشرطان المجمّدان في المرحلة 1 (قرارات معمارية غير قابلة للتجاوز)

1. **الـ Seq يُمنح عند الـ Commit، لا عند إنشاء الصف.** كل عملية تجارية
   (فاتورة 5–15 صفاً) = **سطر واحد في `OperationLog` يأخذ Seq واحداً** بعد نجاح الحفظ كاملاً،
   وكل صفوف العملية تشير إليه — وإلا يتخلل ترتيب العملية صف من جهاز آخر وتفسد إعادة الحساب المشتق.
2. **كل الكتابات تمر عبر مسار واحد (Unit of Work)** يضمن: (أ) ذرّ Seq،
   (ب) سجل العملية، (ج) تعيين `SyncId`/`OriginDevice` عند الإنشاء.
   الحفظ المباشر من الـ ViewModel ممنوع للعمليات التجارية.

**التمييز بين الجدولين (يمنع الخلط):**
- `OperationLog` = سجل الأعمال/التدقيق (من ألغى؟ من عدّل التسوية؟ متى؟) — المرحلة 1، ويمنح Seq.
- `SyncLog` = سجل النقل في الشبكة (المرحلة 2). **وحدة المزامنة = العملية** (سلّة الصفوف المرجع إليها بـ `OpSeq`) لا الصف الفرد.
- النظام: `OperationLog` وُجد قبل `CloseDay`/`StockAdjustment` لأن الإقفال والتسوية **هما أنفسهما عمليات تُسجَّل** في السجل.

## 3. التعارض والخلافات

- الترتيب داخل الجهاز: بالـ Seq فقط. عبر الأجهزة: لا مقارنة بساعة النظام.
- تعارض = تعديلان على نفس الصف من جهازين قبل المزامنة → الطرفان يُحفظان في `SyncConflicts`.
- الحسم **مركزي على MAIN فقط**؛ بقية الأجهزة تعرض «خلافات معلّقة» بلا أزرار قرار (إلا حقل التسمية المعروض LWW بقرار المدير الصريح).
- **البيع لا يُحجب بسبب خلاف بأي حال** — يُباع بالقيمة المحلية الظاهرة، ويُوسَم الصنف «قيمته قيد المراجعة» في الفاتورة والتقارير، ويُرحَّل الحسم.
- تقليل الخلافات من المنبع: ملكية الكيان لجهازه الأصلي (OriginDevice):
  - P تملك الهواتف، A الإكسسوارات، M قطع الصيانة؛ تصميم الشاشات يمنع تعديل غير المالك (غير المالك لا يعدّل إلا بالعرض للضرورة).
  - **«الملكية تحدد من يعدّل لا من يحسب»** — الأثر الحسابي نتيجة عمليات مسجّلة (مبدأ 5)، فلا تعديل متبادل على صف الآخر.
- **الفاتورة المشتركة (هاتف+إكسسوار)**: الفاتورة تعود لجهاز **منشئها** `OriginDevice` (من ضغط حفخ)، أما أثر **كل سطر** فيخصم من **مالك فئة المنتج** (الغطاء → مخزون A، الهاتف → مخزون P).
- **صيانة تستهلك قطع A**: ملك المنتج تبقى لـA؛ M يصدّر نوع عملية `RepairPartUsage { product, qty, repairId }` → الحساب المبني يخصم من مخزون المنتج تلقائياً — **بلا أي كتابة على صف المنتج من M**، فلا يدخل نطاق الخلافات أصلاً.

## 4. الشبكة والتشغيل (بيئة منزلية)

- المزامنة **خدمة خلفية دائمة** على كل حاسبة تبدأ مع ويندوز — لا تُغلق مع نافذة البيع.
- الاكتشاف: **UDP Broadcast + نبض Heartbeat دوري** بين الأقران (يُتسامح مع تغيّر IP)؛ + قائمة أقران؛ يُفضَّل تثبيت IP من الراوتر (DHCP Reservation) كخطوة ثانوية اختيارية.
- إعادة محاولة تلقائية بفواصل متدرجة (10ث/30ث/2د/5د) + **jitter** لتفادي تزامن الأجهزة؛ لا يُعلَّن فشل إلا بعد 5 محاولات.
- أمان: مفتاح شبكة سري مشترك + تقييد المنفذ في Windows Firewall على عناوين الأجهزة الأربع + ربط المستمع بالشبكة المحلية + **HMAC بالتسلسل** ضد إعادة التشغيل (replay)؛ TLS لاحقاً.
- بوابة إصدارات: لا مزامنة قبل اتفاق SchemaVersion؛ رسالة «حدّث بقية الأجهزة».
- مصافحة إقران جهاز جديد تتطلب **موافقة صريحة من MAIN** (DeviceName يُعرض: «أنت تزامن مع هاتف-P»).
- جهاز جديد/بديل: يطلب صورة كاملة (baseline) من الأقران — لا يبدأ بسجل فارغ.

## 5. طبقة التحقق — «كشف لا إصلاح»

- بعد كل دورة: ملخص (عدد الصفوف + تجميع معرّفات) لكل جدول حساس.
- + **SUM مالي دوري** (إجمالي الديون، إجمالي المبيعات) — لأن الملخص لا يكشف فساد قيمة مضمّنة.
- أي اختلاف: تنبيه فوري يُظهر الفرق + القيمة في كل جهة.
- **لا تصحيح تلقائي أبداً** — الاستعادة بأمر صريح من المدير موثَّق.

## 6. السجل والضغط

- `SyncLog` يُحفظ دائماً كسجل تدقيق — **لا ضغط في الإنتاج**.
- عند الحاجة الطويلة الأمد: لقطة مادّية (`StockSnapshot`/`BalanceSnapshot`) عند توالي معيّن
  ثم ضغط — وإعادة الحساب = اللقطة + Σ العمليات اللاحقة. (خاصية متقدمة اختيارية.)

## 7. المزامنة ليست نسخاً احتياطياً ⚠️

- نسخ احتياطي ليلي مستقل (SQLite Backup API — لا نسخ الملف) من **MAIN** (لأنها تجمع كل ما تزامن) بالتناوب إلى قرص خارجي/سحابي، **آخر 30 نسخة**.
- **تمرين استعادة دوري (Restore Drill) كل ربع** — نسخة بلا اختبار استعادة حقيقي = خيال.
- الحذف الجماعي الخاطئ ينتشر عبر المزامنة بكفاءة — النسخ الاحتياطي هو خط الدفاع الوحيد (وهو سبب استقلاله التام عن المزامنة).

## 8. Schema جداول المزامنة

كل الجداول تُنشأ عبر migrations لطيفة؛ كل جدول مشمول يضيف الأعمدة القياسية أدناه.
المفتاح المحلي `Id INTEGER AUTOINCREMENT` داخلي فقط — المفتاح المتزامن هو `SyncId`.

### 8.1 الأعمدة القياسية لكل جدول مشمول
| العمود | ملاحظة |
|---|---|
| `SyncId TEXT` | UUID دائم يُنشأ عند الإنشاء، **لا يتغير أبداً** (المبدأ 3) |
| `OriginDevice TEXT` | معرف الجهاز المنشئ (مثل `P-…`، `A-…`، `M-…`، `MAIN-…`) |
| `UpdatedSeq INTEGER` | آخر `Seq` طُبّق على هذا الصف — لكشف «تعديل محلي غير مرسَل» قبل التطبيق |
| `DeletedAt INTEGER` | NULL = حي؛ قيمة = Tombstone (المبدأ 6) |
| `SyncSchemaVersion INTEGER` | إصدار مخطط الصف |

### 8.2 `SyncLog` (سجل الدلتا لكل جهاز)
| العمود | النوع | ملاحظة |
|---|---|---|
| `Id` | INTEGER PK | تتابع محلي |
| `DeviceId` | TEXT | صاحب هذا السجل |
| `Seq` | INTEGER | تتابع صارم داخل `DeviceId` — مع `DeviceId` يشكّل `UNIQUE (DeviceId, Seq)` مفتاح الـ idempotency |
| `Kind` | TEXT | `Create` / `Update` / `Tombstone` |
| `EntityName` | TEXT | اسم الجدول الهدف |
| `EntitySyncId` | TEXT | `SyncId` الصف |
| `PayloadJson` | TEXT | الصف كاملاً بعد التغيير (شاملاً القياسية) |
| `SentAtLocal` | INTEGER | ساعة الجهاز المحلي — **توثيق فقط، لا تُقارن عبر الأجهزة** |

تطبيق دلتا: موجود `(DeviceId, Seq)`؟ → تخطٍّ فوري (idempotent). لا حذف من السجل في الإنتاج (البند 6).

## 9. خوارزمية عودة MAIN

1. قلع → استطلاع الأقران (UDP broadcast + قائمة).
2. مصافحة: هوية + إصدار Schema + متواليات كل طرف.
3. تبادل الدلتا الناقصة بالترتيب، داخل Transactions، Idempotent بـ (DeviceId, Seq).
4. صف متعارض → SyncConflicts (لا تطبيق).
5. إعادة حساب الـ derived محلياً.
6. مقارنة الملخصات + SUM المالي → اختلاف؟ تنبيه (كشف لا إصلاح) : ACK نهائي.

## 10. الاختبارات الفوضوية (شرط الإطلاق)

1. فصل كهرباء MAIN في منتصف تطبيق دلتا (مراراً، نقاط مختلفة).
2. **انطفاء جهازين معاً في منتصف تبادل دلتا** (سيناريو الراوتر/الكهرباء المنزلي).
3. جهاز يغيب 30 يوماً ثم يعود بدلتا ضخمة.
4. جهازان يعدّلان نفس الزبون 10 مرات بالتناوب → لا فقدان، كل الطرفان في الخلافات.
5. قاعدة تالفة على جهاز واحد والباقي سليم → كشف + استعادة يدوية موثقة.
6. إغلاق نافذة البيع أثناء المزامنة → الخدمة الخلفية تُكمل.
7. جهازان بنفس الاسم/الباركود → تحذير مكرر، لا حذف.
8. انقطاع الراوتر 15 دقيقة → كل جهاز يعمل offline ثم يستأنف تلقائياً.
9. **تعديلان لنفس الفاتورة في فترة سماح من جهازين ثم إقفال** → الخلاف يؤجَّل، والبيع يستمر.
```
