## 0. خلاصة تنفيذية (لمن يريد الجوهر)

خطوة النشر §11 ستُنفَّذ بلا مفاجآت إذا طُبِّقت **قائمة فحص ما قبل التشغيل (§4) + بروتوكول اليوم الأول (§5)**
مع مراعاة ست نقاط مصدرها البحث:

1. **جدار الحماية**: قاعدة **واردة** على **كل** مضيف، `TCP 45678`، `RemoteAddress = LocalSubnet` و`Profile = Private`
   فقط — لا «كل العناوين الأربعة» في الصياغة العامة، بل نطاق الشبكة المنزلية (الأمر الجاهز §4C).
2. **الشبكة**: **DHCP Reservation** (ربط بمنافذ الاتصال) أفضل من IP ثابت يدوي؛ تُراجع مرة/سنتين.
3. **الساعة**: تاريخ الفاتورة من ساعة الجهاز — تأكد «المزامنة التلقائية» + `w32tm /query /status`
   على كليهما قبل التشغيل (الدرس: انحراف يوم = رقم بتاريخ خاطئ).
4. **السرّ**: يولَّد **32 بايت / 256 بت** بأداة CSPRNG (لا نفس المعروفة، لا كلمة سياق)؛
   **تدوير السرّ = الطريقة الوحيدة المسنَدة لإخراج جهاز من الشبكة** (العضوية = حيازة السرّ).
5. **نسخة قبل اليوم الأول**: `VACUUM INTO` (ما يفعله `BackupService` فعلاً) + `integrity_check` + عدّ —
   النسخة غير المُسترجَعة «أمل لا نسخة»؛ يجري Restore Drill ربعياً (R2 — منجز بالفعل).
6. **التوازي 30 يوماً**: مقارنة **أسبوعية باسم محدد** ومكتوبة، و**تاريخ توقف معلَن قبل البدء** —
   بلا مقارنة يتحول التوازي من فحص إلى تكرار وحب.

معيار القبول النهائي للخطوة يبقى **387 × 5 أخضر** وEXIT=0 وصفر تحذيرات، ومن بعده (على الأجهزة)
اليوم الكامل بلا تعارض + البادئة حاضرة في فواتير الطرفين (معايير §11 الحالية في DEPLOY-PAIRING).

## 1. تأكيد المعمارية من المصادر (تصميمنا صحيح — بلا تغيير كود)

| مبدأ من المصادر | ما تقوله المصادر | موضع التحقق في تصميمنا |
|---|---|---|
| لا قاعدة SQLite حيّة مشتركة عبر شبكة/مجلد متزامن | WAL يتطلب مشاركة ذاكرة بين المعالجات على **نفس المضيف** (sqlite.org/wal.html)؛ نسخ الملف الحيّ يخطئ أو يترك قاعدة «تقرأ بشكل مقنع» ببيانات قديمة (SQLPro/النسخ الساخنة) | تصميمنا: قاعدة **محلية** + نقل **دلتا** عبر TCP (`DeltaBuilder/DeltaApplier`, علامات الماء `(OriginDevice,OriginSeq)`) — صحيح بتوصية المصادر |
| أولوية الدفعة الدائمة كجذر موثوق | نمط **Outbox** + idempotency + سجل تسوية (من أدبيات offline-first) | `OperationLog` + `Seq` فور Commit؛ تطبيق idempotent؛ `SyncLogs.UNIQUE(DeviceId,Seq)` |
| العضوية = حيازة السرّ | أنظمة الربط/النظير: من يملك السرّ فهو عضو؛ **إخراج جهاز = تدوير السرّ** | حارس السرّ 1.19 (رفض القيمة المعروفة + رفض بلا اتصال) — متطابق |
| ساعة منطقية لا جدارية للترتيب | جدار الوقت غير موثوق للترتيب بين الأجهزة | ترتيب الاستحقاق بـ`Seq` المنطقية؛ جدار الوقت يُستخدم للعرض/التاريخ فقط |
| حذف محفوظ لا يُمسح | tombstones تُحتفظ ≥ نافذة الانقطاع كي لا تعود الأصول | `StaysDeleted`/الحذف المُعلَّم (P3.1) |
| نسخة قاعدة حيّة صحيحة | `VACUUM INTO` أو Online Backup API ثم `integrity_check` + عدّ (sqlite.org + SQLPro) | `BackupService` = `VACUUM INTO` + تحقق سلامة (SYNC-DESIGN 1.5) — متطابق تقريباً بالحرف |

**الخلاصة**: لا حاجة لأي تعديل برمجي قبل القيام بالخطوة؛ الدراسة تصبُّ بالكامل في التشغيل.
(تأكيد إضافي: ملف القاعدة الحقيقي خارج أي مجلد مزامنة/سحابي — 《إبقِ القاعدة الحية خارج المجلدات المتزامنة》.)

## 2. فجوات التشغيل التي رصدها البحث (ومعالجتها §4–§6)

1. **جدار الحماية** — لا شيء في DEPLOY-PAIRING §3/§4 يحدد **كيف** تُفتح القاعدة (أمر، نطاق، ملف شخصي، تحقق، اختبار سلبي).
2. **الشبكة** — «DHCP Reservation أو IP يدوي» بلا طريقة: أين الحجز، كيف يربط MAC، ماذا نتجنب.
3. **الوقت** — لا خطوة لتزامن الساعة رغم أن **تاريخ** الفاتورة من ساعة الجهاز.
4. **توليد السرّ** — «سرّ قوي» بلا عيار: الطول، المصدر، الحفظ، التدوير (وابن إخراج الجهاز).
5. **نسخة نقطة العودة** — لا خطوة «نسخة مؤكدة قبل الاقتران» (النسخة بلا استرجاع مُجرَّب = أمل).
6. **التوازي 30 يوماً** (§11/3) — لا آلية مقارنة أسبوعية ولا موعد توقف معلَن (الفخ المعروف: التوازي اللانهائي).
7. **قرار القطع go/no-go** — لا معيار يحسم «نمرّ» مقابل «نتراجع» في اليوم الأول.

المعالجة: §4 قائمة فحص (تغلق 1–5)، §5 بروتوكول اليوم الأول (يغلق 7)، §6 التوازي والمراقبة (يغلق 6).

## 3. الوصفات الجاهزة (أوامر ناسخة-لصق، بحروف موثقة)

### 3A. استكشاف الشبكة (على كل جهاز، قبل القاعدة)
```powershell
ipconfig /all          # اكتب وحدة الاسم + IPv4 + عنوان MAC (العمود Physical Address)
Test-NetConnection 192.168.1.20 -Port 45678   # سلبي قبل فتح القاعدة: متوقع False (اختبار سلبي شرعي)
```

### 3B. DHCP Reservation (في الموزع/الراوتر — خارج الكود)
- من لوحة الراوتر: «DHCP → Reservations» → أضف لكل مضيف: عنوان MAC + IP ثابت.
- القاعدة: الحجز **خارج نطاق التجمع** أو ضمنه **بلا تعارض**؛ اربط **منفذ الاتصال** (Ethernet)،
  وأطفئ «عشوائية MAC» (Windows «عناوين عشوائية» = Off) وإلا انكسر الحجز.
- تحقق: أعد تشغيل الشبكة (`ipconfig /release; ipconfig /renew`) ثم `ipconfig /all` → نفس الـ IP.
- مراجعة دورية للحجوزات (تداي: مرة/سنتين) عند تغير قائمة الأجهزة.

### 3C. قاعدة جدار الحماية (على كل مضيف، قابلة للإعادة بلا ضرر — idempotent)
```powershell
New-NetFirewallRule -Name 'PhoneAccounting-P2P-45678' `
  -DisplayName 'PhoneAccounting P2P Sync (TCP 45678)' `
  -Direction Inbound -Action Allow -Protocol TCP `
  -LocalPort 45678 -RemoteAddress LocalSubnet -Profile Private

# تحقق من القاعدة نفسها
Get-NetFirewallRule -Name 'PhoneAccounting-P2P-45678' | fl Name,Direction,Action,Profile,Enabled
Get-NetFirewallPortFilter -AssociatedNetFirewallRule 'PhoneAccounting-P2P-45678' | fl Protocol,LocalPort
Get-NetFirewallAddressFilter -AssociatedNetFirewallRule 'PhoneAccounting-P2P-45678' | fl RemoteAddress

# تحقق وظيفي (إيجابي)
Test-NetConnection 192.168.1.20 -Port 45678     # متوقع True بعد إعادة تشغيل التطبيق
```
- أسس القاعدة (من إرشادات Microsoft لجدار الحماية): **نطاق** وليس «الكل»؛ المنفذ TCP فقط؛
  الملف الشخصي **Private** (وليس Public) — شبكة المنزل Private؛ لا حاجة لقاعدة صادرة (الاتصال الصادر
  stateful)؛ الاسم ثابت حتى لا تتكدس نسخ مكررة عند تكرار التطبيق.

### 3D. تزامن الساعة (على كل جهاز — يؤثر في **تاريخ** الفاتورة)
```powershell
w32tm /query /status          # ألقِ نظرة على: ٤ Source + Last Successful Sync Time
w32tm /stripchart /computer:time.windows.com /samples:5 /dataonly   # انحراف ≈ 0
```
- الإعداد الافتراضي لويندوز: التزامن التلقائي مع `time.windows.com` «مفعَّل» —
  تحقق منه في إعدادات الوقت/المنطقة (مزامنة تلقائية = On). إن كانت الشبكة بلا إنترنت يوماً:
  انحراف بسيط (دقائق) لا يلمس الترتيب (Seq منطقية) لكن اجعل **التاريخ** صحيحاً دائماً.

### 3E. النسخة الاحتياطية قبل الاقتران (نقطة العودة)
- عبر التطبيق نفسه (نسخة `BackupService`، VACUUM INTO — كالموصى به).
- تحقق، لا تولّ: `PRAGMA integrity_check = ok` + عدّ فواتير اليوم في النسخة = نفس عدّ الأصل.

### 3F. توليد السرّ المشترك (256 بت / 32 بايت)
```powershell
$bytes = New-Object byte[] 32
[System.Security.Cryptography.RandomNumberGenerator]::Fill($bytes)
([BitConverter]::ToString($bytes)).Replace('-','')   # 64 خانة سداسية — انسخها للجهازين
```
- المصدر: CSPRNG للنظام (مثل `/dev/urandom` أو `CryptGenRandom`) — التوليد **على MAIN** ثم إدخال
  القيمة نفسها على الجهازين في نافذة واحدة (SettingsView ← سرّ مشترك ← حفظ ← إعادة تشغيل).
- **لا** تُخزَّن في ملف نصي على الجهازين؛ احفظها في مدير كلمات مرور، وسجّل الوصف/التاريخ/الأجهزة.
- التخزين في `AppSettings` بالقاعدة محلي — مقبول للمحل الواحد مع حماية الملف (خاص بالمستخدم).
- **التدوير = إخراج جهاز**: لإخراج أي جهاز من الشبكة، غيّر السرّ على **كل** الأجهزة الباقية في نفس
  النافذة ثم أعد تشغيل التطبيق. كل جهاز لا يعرف السرّ الجديد خرج تلقائياً (مصافحة تفشل).

## 5. بروتوكول اليوم الأول (القطع على الزوج) — مع قرار go/no-go

التسلسل (مقيس على إرشادات go-live: خطوة ← شرط مسبق ← إجراء ← تحقق ← تراجع):

| الخطوة | الشرط المسبق | التحقق | التراجع إن فشلت |
|--------|-------------|--------|-----------------|
| 1. ضبط MAIN (دور/سرّ/منفذ/حفظ) | الفحص 4-مكتمل | رسالة الحفظ + إعادة تشغيل + الشاشة تعرض الدور/السيّد | أعد الضبط على الحالة القديمة |
| 2. ضبط الكاشير (نفس السرّ) | الخطوة 1 تمت | نفس التحقق + `DeviceIdText` يختلف عن MAIN | أعد الضبط |
| 3. `SyncPeers` متقابل (host:port) | الخطوتان تمتا | `NormalizePeers` يطبع `host:port` صحيحاً | أعد الإدخال |
| 4. «زامن الآن» يدوياً | الخطوة 3 | مصافحة ناجحة + `pulled/pushed` محدّثان على شاشة المزامنة | راجع القاعدة 3C/3A (شبكة) |
| 5. بيع حقيقي على الكاشير | الخطوة 4 | الرقم `F-<بادرة>...` يعرض بادئة **الكاشير** | — |
| 6. وصوله MAIN بلا خرق `InvoiceNumber` | الخطوة 5 | فاتورة الكاشير ظاهرة على MAIN + `UNIQUE` سالم | — |
| 7. **بعد ساعات الدوام**: إقفال اليوم على الجهازين | لا تجارة مفتوحة | `CloseDay` المقفل + منع تعديل | — |
| 8. **المزامنة تسبق النسخة الليلية** | الخطوة 7 | `FinancialTotals.Verify` + عدّ اليوم — لا فجوة → نسخة MAIN (30) | قرار R3 |

**قرار القطع**: إن فشلت مصافحة اليوم الأول بعد الفحوصات 4–6 → **لا تفتح §11** وعُد إلى «قائمة الفحص»؛
إن حصلت المصافحة والتلاحم ومرّ يوم كامل بلا تعارض → «GO». تعارض حقيقي وحيد مصيره شاشة
الخلافات (1.13) وحسم اليوم نفسه (§8، سطر قبول خلاف اليوم الأول) — لا يفتح نافذة تراجع.

**فترة استقرار (يوم واحد بعد القطع)**: مراقبة مكثفة لليوم التالي: حالة الأقران خضراء على شاشة
المزامنة، لا تعارض معلّق، راجع بطاقة «دخول فواتير اليوم نفسه» (نفس اليوم، ليس «يُرحل للغد») —
هو المؤشر الذي يكشف التراجع مبكراً.

## 6. التوازي 30 يوماً والمراقبة الدورية (موازٍ لـ §11/3–4)

- **قواعد التوازي الصحيحة** (من أدبيات parallel run): نطاق واحد (فواتير البيع فقط)، **أربعة أسابيع**
  تشمل إقفال شهر، مقارنة **أسبوعية باسم محدد وساعة واحدة** «فروق ← سبب لكل فرق» (السبب أهم من العدد:
  نسيان إدخال / تعريفان مختلفان / الخطأ في السجل القديم)، و**تاريخ توقف معلَن قبل البدء** لا يُحرَّك.
  الوصفة العملية: جوَّل مقارنتك الأسبوعية إلى «قائمة فروق باسم مدير» تُقارن مع ورقة المعرض؛
  الفرق بلا تفسير = صفر مسموح، وإن ظهر يُوقف قبل الأسبوع الثالث.
- **القطع الفعلي**: لا تقطع في آخر/أول أسبوع من الشهر؛ يوم منتصف الشهر، و«اجمع الدفتر الورقي
  فيزيائياً بتاريخ على غلافه» — يغادر المحل لكنه يُحتفظ به كمرجع (لا يُرمى). 
- **بعد أسبوعين من التقاعد**: اسأل «ماذا بقي عند الكاشير خارج النظام؟» — جداول خاصة تظهر في
  هذا التوقيت؛ فهنا يكمن التراجع الصييت.
- **الدورة اليومية الثابتة** (موجودة في DEPLOY-PAIRING §5 — تبقى): إقفال → مزامنة تسبق النسخة →
  Verify + عدّ → نسخة MAIN (احتفاظ 30)؛ وراجِع ليلاً «لا تعارض معلّق».
- **ربعياً**: Restore Drill R2 (12 فحصاً منجزاً) + مراجعة حجوزات DHCP + مراجعة السرّ (تدوير عند الشك).

## 9. تقييم كروم بوك x86_64 — جهاز اختبار لتقنيات المزامنة (2026-09-16)

> **الهدف (من المستخدم)**: استخدام كروم بوك — معالجه **Intel/AMD (x86_64)** — **لاختبار التقنيات
> المبنية** (دلتا TCP، idempotency، علامات الماء، حارس السرّ، التعارضات) لا كجهاز إنتاج، بانتظار
> توفر الحواسيب الفعلية. **القيود المثبتة**: التطبيق `PhoneAccounting.App.csproj` مشروع **واحد**
> مترابط `net10.0-windows`+`UseWPF` (واجهات + خدمات + قاعدة في ملف واحد) → **لا يُشغَّل كما هو على ChromeOS**.

### 9.1 خيارات الاستفادة (مصفوفة جهد/مخاطرة/ماذا يُختبَر)

| الخيار | الجهد | يعمل فعلاً؟ | ماذا يختبر من تقنياتنا؟ | الحكم |
|---|---|---|---|---|
| **1. عميل رفيع عبر RDP** (تطبيق «Windows App» من Play، أو Remmina في Crostini) | يقارب الصفر | نعم، اليوم | **شيئاً** — الجلسة على MAIN نفسه: نفس `DeviceId` ونفس القاعدة، فليس «عقدة ثانية» أصلاً | غير مجدٍ للاختبار |
| **2. Wine في Crostini** (x86_64 فقط) | متوسط | مشكوك: WPF تحت Wine غير موثوقة (.NET حديث + رسوميات) فحتى الإقلاع غير مضمون | غير صالح — لا يمكن الوثوق بالفحص فوق طبقة ترجمة هشة | مرفوض ببيان |
| **3. عقدة اختبار بلا واجهة (Peer Headless)** — مشروع `net10.0` (linux-x64) يعيد استخدام محرك المزامنة + القاعدة، يعمل في محطة Linux (Crostini) | كبير لكن محدود بأخرى | **نعم، بموثوقية أصلية** (C# على Linux رسمياً، SQLitePCLRaw له حزم linux-x64) | **كل التقنيات**: مصافحة + سرّ + SchemaVersion، دلتا TCP حقيقية عبر LAN، idempotency، علامات الماء، استدراك/تعارض قابلان للحسم من MAIN — عبر **جهازين/نظامين فعليين** | **المُوصى به** |
| **4. إصدار واجهة Linux كاملة (Avalonia)** | كبير جداً | نعم | كل ما سبق **بواجهة كاشير كاملة** | مفرط لهدف «اختبار التقنيات»؛ يُرجأ لحين قرار إنتاج |

### 9.2 الخيار 3 عملياً (الخطوط العريضة للقرار — لا تنفيذ بعد)

1. **استخراج الطبقة العالمية**: نقل `Data` + محرك المزامنة (SyncPeer/SyncScheduler/DeltaBuilder/
   DeltaApplier/الحارس 1.19/علامات الماء) من مشروع WPF إلى **مكتبة فئة `net10.0`** (بلا `-windows`)
   — **إعادة تنظيم صفر تغيير سلوك** تُثبَّت بإعادة بوابة 387×5 قبل المتابعة.
2. **مضيف تحكم** (console thin): يقرأ إعدادات (`DeviceRole=Cashier` افتراضياً/`SyncSecret`/`SyncPeers`/
   `SyncPort`) من قاعدة محلية على نمط `AppSettings`، ويُشغّل `SyncScheduler` — لا شاشة.
3. **سيناريو تدريب عبر الجهازين (Cross-Device Drill)**: نصي/سكربت منضبط (لا داخل عداد 387) يقيس:
   MAIN (ويندوز) ↔ العقدة (كروم بوك عبر LAN): دلتا في الاتجاهين، إعادة سحب idempotent، رفض سرّ
   مختلف، رفض SchemaVersion، ثم حسم خلاف حقيقي من MAIN — ناتجه سجل تمرير/فشل.
4. **شبكة Crostini**: الاتصال **الصادر** من كروم بوك إلى MAIN سهل (NAT) وفيه يختبر الدلتا أصلاً
   (سحب/دفع/دورة كاملة)؛ **الواردة** إلى الحاوية تتطلب تمرير منفذ الحاوية
   (`vmc`/إعدادات Crostini `--forward-ports`) — خطوة اختيارية ثانية بمستندها.

### 9.3 مخاطر مرحلية (موثَّقة للتقييم)

- **الاستخراج**: خطر إعادة تنظيم — يُخفَّف بإعادة بوابة 387×5 قبل أي خطوة لاحقة (عادت التشغيلات تُعَد
  كما في CERTIFICATE بند 10).
- **تثبيت .NET 10 في حاوية Debian 12**: مسار رسمي مدعوم (`dotnet-install` أو حزم apt) — x86_64 سليم.
- **طبعة SQLite الأصلية**: `SQLitePCLRaw.bundle_e_sqlite3` تدعم linux-x64 — لا حزمة خارجية أخيراً.
- **Wine مرفوض بالبيان**: فحصٌ فوق ترجمة هشة = ادعاء بلا صلاحية؛ لا يُعتمد كمسار اختبار.

### 9.4 القرار المطلوب من المستخدم

هل نعتمد **الخيار 3** كمرحلة «مختبر تقنيات كروم بوك» (تُفتح كبند جديد في خطة-الخطوة-القادمة مع
بوابة 387×5 تأكيدية بعد الاستخراج)، أم نكتفي بتسجيل التقييم رهن توفر الحواسيب الفعلية؟ هذا القرار
**لا يغيّر تشغيل §11 الحالي** — أيٌّ منهما النشر الفعلي يبقى على ويندوز كما هو موثّق.

## 10. المختبر المحلي المعتمد: حاسبة افتراضية (Hyper-V) — القرار النهائي للمستخدم

> **قرار المستخدم (2026-09-16)**: بدل كروم بوك، يُنشأ **كمبيوتر افتراضي داخل هذا الجهاز**
> (إمكانياته كافية) وتُختبر المزامنة على «جهازين»: **الحقيقية = MAIN** و**الافتراضية = الصيانة (مثلاً)**.
> قسم §9 يُحتفظ به كمرجع تقييم — لا يُنفَّذ. SYNC-DESIGN **1.24** يُوثّق القرار.

### 10.1 لماذا هذا هو المسار الأفضل

- **بلا تغيير كود**: الواجهة WPF نفسها على الجهة الثانية (لا كتبوتر بوك ولا إصدار Linux).
- **نفس طوبولوجيا §11**: الجهازان على **نفس نطاق الراوتر** (`192.168.1.x`) عبر **External virtual switch**
  — دلتا TCP، مصافحة السرّ، SchemaVersion، علامات الماء، والتعارضات تُختبَر تماماً كما على أجهزة فعلية.
- **هوية مستقلة**: الآلة الافتراضية تبذر `DeviceId` خاصاً بها + قاعدة `%LOCALAPPDATA%` خاصة للآلة —
  فبادئة `F-` تختلف بين الجهازين (فحوصات H1 تنطبق حرفياً بقيم مقيسة على الجهازين).
- **قياسات الجهاز الفعلية (2026-09-16، من الجهاز)**: Windows 11 **Pro** (SKU 48)، ذاكرة **15.7GB**،
  `i7-13620H` (10 أنوية/16 خيطاً)، `HypervisorPresent=True`+`vmcompute` يعمل ⇒ **Hyper-V** متاح بلا سعر
  إضافي؛ C: متاح **121GB**. التخصيص المقترح للآلة: **~8GB** ذاكرة و**60GB** قرص (تبقى ~7GB و~60GB للأصل).

### 10.2 خطوات الإنشاء (طبيعة الأشياء؛ تتطلب نافذة PowerShell **مرفِّعة** = تشغيل كمسؤول)

**أ. تفعيل دور Hyper-V بالكامل (مرة واحدة، ثم إعادة تشغيل إن طُلب):**
```powershell
Enable-WindowsOptionalFeature -Online -FeatureName Microsoft-Hyper-V -All
# بعد إعادة التشغيل: تحقق
Get-WindowsOptionalFeature -Online -FeatureName Microsoft-Hyper-V | fl State   # = Enabled
```

**ب. تنزيل ISO لويندوز 11**: من صفحة Microsoft الرسمية «Download Windows 11 Disk Image (ISO)»
(الخيار الثامن المللي في md والجهاز هو x64) — هذا الملف يُرفق للآلة. ملاحظة ترخيص: نسخة **التقييم**
كافية للاب للاختبار؛ التفعيل الكامل يتطلب مفتاحاً (المبدأ: لا تعتمد على كسر حماية).

**ج. إنشاء مبدّل الشبكة الخارجي + الآلة (عبر نفس الجلسة المرفِّعة):**
```powershell
# مبدّل خارجي على كرت الشبكة الفعلي (يحصل الجهاز الثاني على IP من الراوتر كالأصل)
New-VMSwitch -Name "LAN-Sync" -NetAdapterName (Get-NetAdapter | Where-Object Status -eq 'Up' | Select-Object -First 1).Name -AllowManagementOS $true

# الآلة (اضبط الاسم/المسار كما تشاء)
New-VM -Name "RepairVM" -Generation 2 -MemoryStartupBytes 8GB -BootDevice VHD `
       -NewVHDSizeBytes 60GB -NewVHDPath "D:\VMs\RepairVM\RepairVM.vhdx" -SwitchName "LAN-Sync"
Set-VMMemory -VMName "RepairVM" -DynamicMemoryEnabled $true -MaximumBytes 10GB
Set-VM -VMName "RepairVM" -ProcessorCount 6
Set-VMDvdDrive -VMName "RepairVM" -Path "C:\Users\Windows 11\Downloads\Win11_24H2_x64.iso"
# ربط الآلة بـ ISO ثم تشغيلها:
Start-VM -Name "RepairVM"; vmconnect localhost "RepairVM"
```
> ملاحظة مسار القرص: إن لم يوجد `D:`، استبدل المسار بـ `C:\VMs\...` (C: متاح 121GB). إن أردت
> واجهة رسومية: افتح **Hyper-V Manager** (القائمة) ثم New → Virtual Machine بنفس القيم.

**د. داخل الآلة الافتراضية**: أفشل ثبّت Windows 11 من الـISO، ثم امنحها تحديثاً وتثبيت .NET Desktop
Runtime 10 إن لزم (أو استخدم النشر المتضمن أدناه فلا حاجة):

### 10.3 تشغيل التطبيق على الجهة الثانية (نشر ذاتي — لا تثبيت .NET هناك)

```powershell
# من مجلد المشروع على الأصل (نافذة عادية):
dotnet publish -c Release -r win-x64 --self-contained true -p:PublishSingleFile=false
# انسخ ناتج:
#   bin\Release\net10.0-windows\win-x64\publish\*  ← إلى الآلة الافتراضية (مجلد مثلاً C:\PhoneAccounting)
```

### 10.4 الاقتران (مطابق لـ §11 خطوتي 1-2، بقوائم §4/§5)

| الجهاز | دور | السرّ المشترك | المنفذ | الأقران | جدار الحماية (واردة) |
|---|---|---|---|---|---|
| الحقيقية (MAIN) | MainServer | نفس القيمة على الجهازين | 45678 | `<IP الآلة>:45678` | `New-NetFirewallRule … 3C` |
| الافتراضية (الصيانة) | Repair | نفس | 45678 | `<IP الأصل>:45678` | الأمر 3C نفسه داخل الآلة |

1. على كل جهاز: «الإعدادات ← المزامنة والاقتران»: الدور + السرّ (الوصفة §3F، 256 بت) + المنفذ + حفظ.
2. جدار الحماية على الجهازين (الوصفة 3C: `LocalSubnet`+`Private`+TCP 45678) — **وعلى الآلة كذلك**.
3. الأقران متقابلان (host:port)، ثم «زامن الآن» يدوياً حتى المصافحة، teleفراغ الدوري 5 دقائق.
4. اختبار فعلي: بيع على الآلة الافتراضية — رقم `F-<بادئة-الآلة>-…` يصل MAIN بلا خرق `InvoiceNumber`؛
   ومخالفة سرّ متعمدة على أحد الجانبين → رفض بلا اتصال (حارس 1.19).
5. بعد ساعات العمل: إقفال اليوم على الجهازين «المزامنة تسبق النسخة» (قرار R3).

> **حارس السرّ 1.19 سيمنع أي تزامن قبل ضبط سرّ مشترك حقيقي** — متعمد: لا قيمة معروفة ولا غياب.
> القاعدة الحقيقية للأصل تبقى كما هي حتى يقرر المستخدم §11 فعلياً (النسخة §3E أولاً).

### 10.5 حدود حديثة (معلنة)

- ترخيص ويندوز داخل الآلة (تقييم/مفتاح) — اجتماعي للاب.
- الـ VM تستخدم جزءاً من الموارد (ذاكرة/قرص/حدات CPU) — بقية ~7GB و~60GB تكفي للتشغيل اليومي.
- أداء الشبكة عبر المبدّل الخارجي ≈ بطاقة أصلية (لا محاكاة امتداد) — كافٍ لدلتا POS حقيقية.
- هذا مختبر فعلي **لكن ليس «جهازي اثنين»** بمعنى نقل الجهاز للفرع — التزامن نفسه هو المستهدف.
